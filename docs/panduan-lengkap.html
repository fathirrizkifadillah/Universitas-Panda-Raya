BAB 1: PENJELASAN KONSEPTUAL TUGAS

1.1. Mengapa Tugas Ini Diberikan?

Secara tradisional, keamanan aplikasi web mengandalkan pendekatan Perimeter-Based Security (Castle-and-Moat): siapa pun yang berhasil masuk ke dalam jaringan internal (misalnya melalui VPN atau berada di jaringan LAN kampus yang sama) dianggap tepercaya secara bebas. Jika penyerang berhasil membobol salah satu celah di perimeter luar, mereka dapat bergerak bebas ke samping (lateral movement) ke seluruh server dan database tanpa rintangan.

Tugas praktikum ini bertujuan mentransformasi pola pikir tersebut menjadi Zero Trust Architecture (ZTA) sesuai pedoman federal Amerika Serikat NIST SP 800-207 yang diterapkan langsung pada application level.

1.2. Tiga Pilar Filosofis Zero Trust

  • 1. Never Trust, Always Verify: Tidak ada permintaan (request) yang dipercaya secara buta, baik yang berasal dari luar jaringan maupun antar-server internal. Setiap request wajib diautentikasi ulang, diverifikasi tanda tangan kriptografisnya, diperiksa device pengirimnya, dan dievaluasi hak aksesnya secara kontinu.
  • 2. Least Privilege (Hak Akses Terendah): Pengguna dan service hanya diberikan izin minimum absolut yang diperlukan untuk menyelesaikan tugasnya pada saat itu. Mahasiswa hanya boleh melihat nilainya sendiri (tidak bisa melihat mahasiswa lain / anti-IDOR). Dosen hanya boleh mengedit kelas yang diampunya sendiri (bukan kelas dosen lain) dan hanya pada jam kerja resmi. Administrator hanya berhak membaca transkrip untuk validasi kelulusan tanpa hak mengubah nilai.
  • 3. Assume Breach (Asumsikan Sistem Telah Ditembus): Arsitektur dirancang dengan asumsi bahwa jaringan internal sudah tidak aman dan penyerang mungkin telah berada di dalam jaringan. Oleh karena itu, Service internal (Service Nilai dan Service Transkrip) tidak boleh diekspos sebagai API publik, wajib memverifikasi Gateway Secret untuk memastikan pemanggil adalah API Gateway resmi, serta tetap memvalidasi token JWT secara mandiri.

1.3. Skenario Bisnis Akademik

Skenario yang dibangun adalah sistem pengelolaan nilai dan transkrip akademik universitas (dinamai PANDAKAD — Universitas Panda Raya). Sistem melibatkan 3 peran pengguna (Mahasiswa, Dosen, Administrator) dan 2 domain microservices yang saling terisolasi (Service Nilai pada port 3001 dan Service Transkrip pada port 3002) yang diproteksi di balik satu pintu gerbang utama: API Gateway sebagai Policy Enforcement Point (PEP) pada port 3000.

3.2. Alur Request Klien (User Request Flow)

  1. Pengguna memasukkan username, password, dan perangkat di halaman login frontend (http://localhost:5173/login).
  2. Frontend mengirim POST /auth/login beserta header X-Device-ID ke Gateway (port 3000).
  3. Gateway memverifikasi hash password (menggunakan bcrypt) dan memeriksa apakah device tersebut terdaftar sebagai milik user tersebut di tabel devices.
  4. Jika valid, Gateway menerbitkan Access Token (RS256 JWT, masa berlaku 10 menit) dan Refresh Token (disimpan hash-nya di DB, masa berlaku 1 hari).
  5. Untuk setiap navigasi atau permintaan data (misalnya membuka nilai), frontend menyertakan Authorization: Bearer <access_token> dan X-Device-ID.
  6. Gateway bertindak sebagai Policy Enforcement Point (PEP):
    • Memvalidasi keaslian tanda tangan token RS256 menggunakan Public Key.
    • Memeriksa status aktif perangkat di basis data.
    • Meminta keputusan ke Policy Engine: mengevaluasi role, kepemilikan data (misal: NIM mahasiswa atau kelas dosen), dan window jam akses (07.00–21.00 WIB).
    • Menuliskan keputusan (ALLOW / DENY) beserta reason code ke dalam tabel audit_events.
  7. Jika keputusan DENY: Gateway langsung memutus koneksi dan mengembalikan HTTP 403 Forbidden. Request sama sekali tidak pernah menyentuh service backend downstream.
  8. Jika keputusan ALLOW: Gateway membersihkan header berbahaya dari request masuk, menyuntikkan header X-Gateway-Secret resmi dari environment server, lalu meneruskan request (reverse proxy) ke Service Nilai atau Service Transkrip.
  9. Service hilir (downstream) memverifikasi ulang bahwa X-Gateway-Secret valid dan token JWT sah sebelum mengeksekusi query database dan mengembalikan payload JSON.

BAB 4: DEEP DIVE MEKANISME KEAMANAN ZERO TRUST

4.1. Kriptografi Asimetris RS256 (Tanpa Regenerasi Kunci saat Restart)

Sistem menggunakan pasangan kunci RSA 2048-bit (Private Key dan Public Key). Kunci dibuat satu kali saat setup sistem awal dan disimpan secara lokal pada file keys/private.pem dan keys/public.pem (yang diabaikan oleh git demi keamanan).

  • API Gateway (Port 3000): Menyimpan Private Key untuk menandatangani Access Token pengguna dan Service Token antar-layanan.
  • Service Nilai (Port 3001) & Service Transkrip (Port 3002): Hanya menyimpan Public Key. Service dapat memverifikasi keaslian dan integritas token secara independen tanpa pernah memiliki hak menerbitkan token baru.
  • Kunci privat tidak pernah di-commit ke repositori dan tidak pernah dibagikan ke browser client.

4.2. Pertahanan Berlapis Antar-Layanan (Assume Breach & Gateway Secret)

Jika seorang penyerang berhasil masuk ke jaringan internal server dan mengetahui IP serta port Service Nilai (3001) atau Transkrip (3002), penyerang tetap tidak dapat mengakses data:

  • Kedua service dilindungi middleware verifyInternalAccess.ts yang mewajibkan keberadaan header X-Gateway-Secret dengan nilai yang cocok persis dengan environment server.
  • Panggilan langsung melalui curl -i http://localhost:3001/nilai tanpa header akan ditolak seketika dengan status 403 FORBIDDEN_GATEWAY_SECRET_REQUIRED.
  • Jika klien mencoba menyuntikkan header X-Gateway-Secret dari browser, middleware sanitizeHeaders.ts di Gateway akan secara otomatis menghapus header tersebut dari inbound request dan menimpanya dengan secret resmi dari environment server.
  • Meskipun penyerang memiliki Gateway Secret, request tetap ditolak jika tidak disertai token JWT bertanda tangan valid (dual verification).

BAB 7: ANTISIPASI PERTANYAAN DOSEN & DEFENSE STRATEGY (FAQ)

Q1: Mengapa arsitektur ini harus dipecah menjadi 3 service terpisah dan tidak dijadikan satu aplikasi monolit Express saja?

Jawaban Kunci:
"Pemisahan proses adalah syarat fundamental dari standar NIST SP 800-207. Dalam Zero Trust, komponen Control Plane (Policy Enforcement Point & Policy Decision Point) harus dipisahkan dari Data Plane / Resource Service. Jika disatukan dalam satu monolit, kebocoran pada salah satu controller dapat mengompromikan seluruh sistem kontrol akses. Dengan memisahkan proses pada port 3000, 3001, dan 3002, kita dapat menerapkan batas kepercayaan (trust boundary) yang nyata, isolasi memori proses, serta membatasi hak akses basis data per layanan."

Q2: Mengapa kita menggunakan algoritma asimetris RS256 dan bukan simetris HS256 untuk tanda tangan JWT?

Jawaban Kunci:
"Pada algoritma simetris seperti HS256, rahasia (secret key) yang sama digunakan untuk membuat token dan memverifikasi token. Artinya, Service Nilai dan Service Transkrip harus memegang rahasia tersebut, sehingga jika salah satu service disusupi, penyerang dapat menerbitkan token palsu sendiri. Dengan algoritma asimetris RS256, Private Key hanya dipegang oleh API Gateway, sedangkan Service hilir hanya membutuhkan Public Key. Service hilir dapat memverifikasi keaslian token secara independen tanpa risiko mampu memalsukan token."

Q3: Mengapa token disimpan di memori dan bukan di LocalStorage browser?

Jawaban Kunci:
"Menyimpan token akses di localStorage merupakan celah keamanan yang sangat rentan terhadap serangan Cross-Site Scripting (XSS), karena skrip JavaScript berbahaya dapat membaca isi localStorage dan mencuri token. Pada sistem kami, token akses disimpan secara aman di dalam memori React state (yang hilang saat tab ditutup), sedangkan Refresh Token dikelola menggunakan sesi berbasis server dengan rotasi token di basis data."

Q4: Apa yang dimaksud dengan 'Idempotent Sync' pada integrasi Service Nilai ke Service Transkrip?

Jawaban Kunci:
"Idempotensi menjamin bahwa suatu operasi yang dieksekusi berulang kali akan menghasilkan kondisi akhir yang sama persis tanpa efek samping negatif. Ketika jaringan mengalami gangguan (timeout) saat dosen melakukan finalisasi, Service Nilai mungkin melakukan pengiriman ulang (retry). Di Service Transkrip, kami menggunakan klausul SQL ON CONFLICT (student_id, class_id) DO UPDATE sehingga data nilai diperbarui secara akurat dan tidak menciptakan duplikasi baris transkrip mahasiswa."

Q5: Mengapa verifikasi X-Device-ID dilakukan di Gateway dan apa batasannya?

Jawaban Kunci:
"Verifikasi X-Device-ID memastikan bahwa request hanya diterima jika berasal dari perangkat yang terikat (bound) pada akun pengguna tersebut di basis data. Batasannya adalah header HTTP dapat dipalsukan jika penyerang mengetahui ID perangkat yang sah. Namun, dalam sistem Zero Trust kami, header ini dievaluasi secara simultan bersama kredensial autentikasi, masa berlaku token, dan window waktu (multi-factor context) sehingga penyerang tidak dapat menembus sistem hanya dengan memalsukan salah satu atribut."
